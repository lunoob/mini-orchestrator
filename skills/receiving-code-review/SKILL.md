# 接收 Code Review

## 核心原则

先验证再改。不清楚就问。技术正确性优先于社交礼貌。

## 响应模式

```
收到反馈 → 读完不急于表态 → 用自己的话复述要求（或提问）
→ 对照代码库核实 → 评估是否适用于本项目 → 技术回应或有理 push back → 逐项修复并测试
```

## 禁止

- 表演式认同（「你说得太对了！」「感谢指正！」）
- 未验证就说「我这就改」
- 只理解一部分就先改一部分（相关项可能互相依赖，须先问清全部）

## 按严重程度处理

| 级别 | 动作 |
|------|------|
| **Critical** | 本轮必须修，修完重跑相关测试 |
| **Important** | 本轮必须修，再输出 `STATUS: IMPLEMENT_DONE` |
| **Minor** | 顺手就修；否则记入 `progress.md` 留待后续 |

## 可以 Push Back 的情况

- 建议会破坏现有功能
- reviewer 缺少上下文
- 违反 YAGNI（功能未被使用）
- 与 spec 或既有架构决策冲突

用技术理由回应，必要时请人类裁决。

## 正确确认方式

```
✅ "已修复：[简述改动]"
✅ "核对后确认问题在 [位置]，已改"
✅ 直接改代码，用 diff 说话

❌ "你说得对！"
❌ "感谢反馈！"
```
